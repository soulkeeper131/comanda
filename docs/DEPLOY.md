# Ко Манда — пускане в продукция

Какво трябва да е настроено на сървъра (Coolify). Всичко е задължително,
освен изрично отбелязаното.

## 0. Две среди

| | Продукция | Тест |
|---|---|---|
| Домейн | `comanda.bg` | `dev.comanda.bg` |
| Клон в git | `main` | `dev` |
| Приложение в Coolify | отделно | отделно — **своя база и свой том** |
| `APP_ENV` | `production` | `dev` |
| `APP_URL` | `https://comanda.bg` | `https://dev.comanda.bg` |
| Stripe | Live ключове (`sk_live_…`) | Test ключове (`sk_test_…`) |
| Търсачки | публичните страници | нищо (robots.txt забранява) |

Тестовата среда показва етикет **Тест** в горната лента. Там се пробва
всяка промяна (вкл. плащане с тестова карта `4242 4242 4242 4242`),
преди да се слее в `main`.

Никога не копирайте продукционната база в теста — там са истински
клиенти и имейли; тестовата среда праща истински писма.

## 1. Променливи на средата

### Задължителни — без тях приложението не тръгва

| Променлива | Стойност |
|---|---|
| `SESSION_SECRET` | Минимум 32 знака. Генерирайте с командата отдолу. |

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Приложението **отказва да стартира** без нея — нарочно, за да не тръгне
никога с познат ключ.

### Задължителни за автоматичните обходи

| Променлива | Стойност |
|---|---|
| `CRON_SECRET` | Минимум 16 знака, същата команда като горе. |

С нея периодичният скрипт (§3) пуска генератора на обходи, изтичането на
оферти и напомнянията. Без нея всичко това става само ръчно — от
**Настройки → Плащания и задачи → Пусни сега**.

### Задължителни при първо пускане

При празна база приложението създава три акаунта, но **само ако**
паролите са зададени. Без тях seed-ът се пропуска и в лога излиза
предупреждение.

| Променлива | За кого |
|---|---|
| `SEED_ADMIN_PASSWORD` | `admin@komanda.bg` |
| `SEED_CLIENT_PASSWORD` | `client@komanda.bg` |
| `SEED_INSPECTOR_PASSWORD` | `inspector@komanda.bg` |

Няма пароли по подразбиране. След първото влизане сменете паролата от
**Профил** и създайте истинските акаунти от **Настройки → Хора**.

### Среда и фирма

| Променлива | Стойност |
|---|---|
| `APP_ENV` | `production` или `dev` (виж §0) |
| `APP_URL` | `https://comanda.bg` / `https://dev.comanda.bg` — за връзките в имейлите и връщането от Stripe |
| `COMPANY_NAME`, `COMPANY_EIK`, `COMPANY_ADDRESS`, `COMPANY_MOL` | Доставчикът във фактурите, общите условия и политиката |
| `COMPANY_VAT` | Само ако фирмата е регистрирана по ДДС |
| `COMPANY_EMAIL`, `COMPANY_PHONE` | Контакт в общите условия и политиката |

Без `COMPANY_*` фактурите казват „Данните на доставчика не са настроени".
Текстовете на `/terms` и `/privacy` са проект — прегледайте ги с юрист.

### Имейл (SMTP) — задължителен за регистрации

Регистрацията праща линк за потвърждение, а „Забравена парола" — линк
за нова парола. **Без SMTP новите клиенти се приемат без потвърждение**
(удобно локално, не и в продукция). Настройва се от **Настройки →
Имейли** или с `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`,
`SMTP_FROM`, `NOTIFY_EMAIL`. Пробвайте с бутона „Тест".

### Плащане с карта — Stripe

Виж §3а. Без Stripe клиентите заявяват пакет без плащане, а админът
отбелязва „Платено по банка".

### По желание

| Променлива | Какво прави |
|---|---|
| `BACKUP_DIR` | Къде отиват резервните копия (виж §2) |
| `BACKUP_KEEP` | Колко копия се пазят (по подразбиране 7) |
| `SMTP_*`, `NOTIFY_EMAIL` | Имейли (може и от **Настройки → Имейли**) |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` | Push известия на телефона |

Банковата сметка за преводи, прагът за предплащане на ремонти и
пакетите с цените се настройват от админския панел, не от средата.

## 2. Резервно копие — задължително

**Без това пускането е рисково.** Загубена база значи загубени абонаменти,
история на обходите и всички снимки.

Образът съдържа `sqlite3` и скриптовете в `/app/scripts/` — копието е
коректно при WAL режим и се проверява с `PRAGMA integrity_check`.

### Scheduled Task в Coolify

Coolify → приложението → **Scheduled Tasks** → нова задача:

| Поле | Стойност |
|---|---|
| Command | `bash /app/scripts/backup-db.sh` |
| Frequency | `0 2 * * *` (всяка нощ в 2:00) |

Архивът съдържа базата **и** снимките.

### Копията да са извън тома на базата

По подразбиране отиват в `data/backups/` — на същия том като базата.
Загуби ли се томът, копията отиват с него. Задайте:

```
BACKUP_DIR=/backups
```

и монтирайте `/backups` като отделен том (Coolify → **Storages**), по
възможност на друг диск или синхронизиран навън.

### Проверка, че копие се възстановява

Непроверено копие не е копие. Веднъж след настройката (Coolify →
**Terminal**):

```bash
bash /app/scripts/backup-db.sh                         # прави копие
bash /app/scripts/restore-db.sh                        # показва наличните
bash /app/scripts/restore-db.sh <архив> --check        # проверява, без да пипа нищо
```

При реална авария:

```bash
bash /app/scripts/restore-db.sh <архив> --yes
```

Преди презаписване скриптът запазва текущата база.

## 3. Периодични задачи — генератор на обходи, оферти, напомняния

Един скрипт прави три неща:

- създава обходите от активните абонаменти **три месеца напред**
  (празниците се прескачат; второ пускане не дублира)
- маркира изтеклите оферти (валидни 7 дни)
- праща напомняния: за оферта без отговор (ден 3 и 6) и за неплатен
  завършен ремонт (ден 3, 7 и 14)

Coolify → **Scheduled Tasks** → нова задача:

| Поле | Стойност |
|---|---|
| Command | `node /app/scripts/cron.mjs` |
| Frequency | `15 * * * *` (всеки час) |

Изисква `CRON_SECRET` в средата (§1). Резултатът се вижда в лога на
задачата, напр. `{"jobs_created":4,"offers_expired":0,...}`.

## 3а. Stripe — стъпка по стъпка

Направете го веднъж в **тестов режим** за dev.comanda.bg и веднъж в
**live режим** за comanda.bg.

1. **Акаунт:** stripe.com → регистрация на фирмата (България, евро).
   Live режимът се отключва след проверка на фирмата и банковата сметка.
2. **Ключ:** Developers → API keys → *Secret key* → `STRIPE_SECRET_KEY`.
3. **Webhook:** Developers → Webhooks → *Add endpoint*
   - URL: `https://comanda.bg/api/stripe/webhook` (за теста — `https://dev.comanda.bg/api/stripe/webhook`)
   - Събития: `checkout.session.completed`, `checkout.session.expired`,
     `invoice.paid`, `invoice.payment_failed`,
     `customer.subscription.updated`, `customer.subscription.deleted`
   - *Signing secret* (`whsec_…`) → `STRIPE_WEBHOOK_SECRET`
4. **Портал за клиенти:** Settings → Billing → *Customer portal* →
   разрешете смяна на карта и история на фактурите; **изключете**
   „Cancel subscriptions" (отказът се прави от приложението, за да
   махне бъдещите обходи — Stripe пак го съобщава чрез webhook, ако
   все пак е включен). Натиснете *Save* — без запазена настройка
   порталът не се отваря.
5. **Повторни опити:** Settings → Billing → *Subscriptions and emails* →
   Smart Retries за ~1 седмица, после *Cancel the subscription*
   (въпрос 5б: около 7 дни гратисен период).
6. **Проверка:** в теста заявете пакет с карта `4242 4242 4242 4242`,
   всяка бъдеща дата и CVC. Абонаментът трябва да се появи при админа в
   „Чакат насрочване", а плащането и фактурата — в Профил на клиента.

Как работи:

- Клиентът избира пакет → плаща първия месец в Stripe → абонаментът
  чака админа да насрочи първия обход.
- Всеки месец Stripe тегли автоматично; всяко плащане става фактура.
- Неуспешно теглене → клиентът и админите получават известие; Stripe
  опитва отново.
- Отказ от клиента → важи до края на платения месец, после спира.
- Отказ на заявка преди първия обход → абонаментът спира веднага, а
  админът връща сумата от таблото на Stripe (Payments → Refund).
- Оферти за ремонт се плащат с карта или по банка; двойно плащане се
  маркира „за връщане" и админите се уведомяват.

## 4. Една инстанция

SQLite е един файл. Coolify **не бива** да е конфигуриран с повече от една
реплика — иначе две инстанции пишат в един файл.

Rate limiting-ът също е в паметта и работи само при една инстанция.

При 10–50 клиента това е напълно достатъчно.

---

## 5. Постоянен том

`/app/data` трябва да е на постоянен том. Там са:

- `sqlite.db` — базата
- `photos/` — снимковите доказателства
- `backups/` — копията (ако не е зададен `BACKUP_DIR`)

Без постоянен том всичко изчезва при всеки деплой.

---

## 6. Миграции

Схемата се мигрира автоматично при старт (`drizzle/`). База, създадена
преди журнала на миграциите, също се поправя сама — в лога тогава пише
`[db] Поправка на схемата: приложени N израза.` Следващото пускане минава
по нормалния път.

**Преди деплой на нова версия** — ръчно копие (§2), за всеки случай.

## 7. Проверка след деплой

```bash
curl -i https://comanda.bg/                 # 200
curl -i https://comanda.bg/api/me           # 401 без сесия
curl https://comanda.bg/robots.txt          # продукция: Allow; dev: Disallow: /
curl https://comanda.bg/api/health          # {"ok":true,"env":"production","commit":"…"}
curl -sI https://comanda.bg/ | grep -i strict-transport   # заглавките за сигурност са там
```

`/api/health` проверява и базата (503 при проблем). Dockerfile-ът има
`HEALTHCHECK` към него, така че Coolify показва контейнера като
unhealthy и го рестартира. В Coolify → **Health Checks** може да се зададе
същият път (`/api/health`, порт 3000) и за Traefik — тогава трафикът не
отива към контейнер, който още не е готов. Същият адрес става и за външен
монитор (UptimeRobot и подобни) — отговорът не съдържа лични данни.

Неприхванатите грешки на сървъра се пишат в лога с час и тип
(`[unhandledRejection]`) — Coolify → Logs.

В лога трябва да пише:

```
[db] Миграциите са приложени (или вече бяха).
```

Ако видите `[db] Seed при старт ПРОПУСНАТ` — липсват `SEED_*`
променливите (нормално, ако базата вече има потребители).

След влизане като админ: **Настройки → Плащания и задачи → Връзки**
показва кои интеграции (Stripe, push, cron) са настроени.
