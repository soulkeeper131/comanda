# Ко Манда — пускане в продукция

Какво трябва да е настроено на сървъра (Coolify). Всичко е задължително,
освен изрично отбелязаното.

---

## 1. Променливи на средата

### Задължителни — без тях приложението не тръгва

| Променлива | Стойност |
|---|---|
| `SESSION_SECRET` | Минимум 32 знака. Генерирайте с командата отдолу. |

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Приложението **отказва да стартира** без нея — нарочно, за да не тръгне
никога с познат ключ.

### Задължителни за автоматичните обходи

| Променлива | Стойност |
|---|---|
| `CRON_SECRET` | Минимум 16 знака, същата команда като горе. |

С нея периодичният скрипт (§3) пуска генератора на обходи, изтичането на
оферти и напомнянията. Без нея всичко това става само ръчно — от
**Настройки → Плащания и задачи → Пусни сега**.

### Задължителни при първо пускане

При празна база приложението създава три акаунта, но **само ако**
паролите са зададени. Без тях seed-ът се пропуска и в лога излиза
предупреждение.

| Променлива | За кого |
|---|---|
| `SEED_ADMIN_PASSWORD` | `admin@komanda.bg` |
| `SEED_CLIENT_PASSWORD` | `client@komanda.bg` |
| `SEED_INSPECTOR_PASSWORD` | `inspector@komanda.bg` |

Няма пароли по подразбиране. След първото влизане сменете паролата от
**Профил** и създайте истинските акаунти от **Настройки → Хора**.

### По желание

| Променлива | Какво прави |
|---|---|
| `NEXT_PUBLIC_APP_URL` | Базов адрес за връзките в имейлите (по подразбиране `https://comanda.bg`) |
| `BACKUP_DIR` | Къде отиват резервните копия (виж §2) |
| `BACKUP_KEEP` | Колко копия се пазят (по подразбиране 7) |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Плащане с карта. Без тях — само по банка |
| `SMTP_*`, `NOTIFY_EMAIL` | Имейли (може и от **Настройки → Имейли**) |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` | Push известия на телефона |

Банковата сметка за преводи, прагът за предплащане на ремонти и
пакетите с цените се настройват от админския панел, не от средата.

## 2. Резервно копие — задължително

**Без това пускането е рисково.** Загубена база значи загубени абонаменти,
история на обходите и всички снимки.

Образът съдържа `sqlite3` и скриптовете в `/app/scripts/` — копието е
коректно при WAL режим и се проверява с `PRAGMA integrity_check`.

### Scheduled Task в Coolify

Coolify → приложението → **Scheduled Tasks** → нова задача:

| Поле | Стойност |
|---|---|
| Command | `bash /app/scripts/backup-db.sh` |
| Frequency | `0 2 * * *` (всяка нощ в 2:00) |

Архивът съдържа базата **и** снимките.

### Копията да са извън тома на базата

По подразбиране отиват в `data/backups/` — на същия том като базата.
Загуби ли се томът, копията отиват с него. Задайте:

```
BACKUP_DIR=/backups
```

и монтирайте `/backups` като отделен том (Coolify → **Storages**), по
възможност на друг диск или синхронизиран навън.

### Проверка, че копие се възстановява

Непроверено копие не е копие. Веднъж след настройката (Coolify →
**Terminal**):

```bash
bash /app/scripts/backup-db.sh                         # прави копие
bash /app/scripts/restore-db.sh                        # показва наличните
bash /app/scripts/restore-db.sh <архив> --check        # проверява, без да пипа нищо
```

При реална авария:

```bash
bash /app/scripts/restore-db.sh <архив> --yes
```

Преди презаписване скриптът запазва текущата база.

## 3. Периодични задачи — генератор на обходи, оферти, напомняния

Един скрипт прави три неща:

- създава обходите от активните абонаменти **три месеца напред**
  (празниците се прескачат; второ пускане не дублира)
- маркира изтеклите оферти (валидни 7 дни)
- праща напомняния: за оферта без отговор (ден 3 и 6) и за неплатен
  завършен ремонт (ден 3, 7 и 14)

Coolify → **Scheduled Tasks** → нова задача:

| Поле | Стойност |
|---|---|
| Command | `node /app/scripts/cron.mjs` |
| Frequency | `15 * * * *` (всеки час) |

Изисква `CRON_SECRET` в средата (§1). Резултатът се вижда в лога на
задачата, напр. `{"jobs_created":4,"offers_expired":0,...}`.

---

## 4. Една инстанция

SQLite е един файл. Coolify **не бива** да е конфигуриран с повече от една
реплика — иначе две инстанции пишат в един файл.

Rate limiting-ът също е в паметта и работи само при една инстанция.

При 10–50 клиента това е напълно достатъчно.

---

## 5. Постоянен том

`/app/data` трябва да е на постоянен том. Там са:

- `sqlite.db` — базата
- `photos/` — снимковите доказателства
- `backups/` — копията (ако не е зададен `BACKUP_DIR`)

Без постоянен том всичко изчезва при всеки деплой.

---

## 6. Миграции

Схемата се мигрира автоматично при старт (`drizzle/`). База, създадена
преди журнала на миграциите, също се поправя сама — в лога тогава пише
`[db] Поправка на схемата: приложени N израза.` Следващото пускане минава
по нормалния път.

**Преди деплой на нова версия** — ръчно копие (§2), за всеки случай.

---

## 7. Проверка след деплой

```bash
curl -i https://comanda.bg/                 # 200
curl -i https://comanda.bg/api/me           # 401 без сесия
```

В лога трябва да пише:

```
[db] Миграциите са приложени (или вече бяха).
```

Ако видите `[db] Seed при старт ПРОПУСНАТ` — липсват `SEED_*`
променливите (нормално, ако базата вече има потребители).

След влизане като админ: **Настройки → Плащания и задачи → Връзки**
показва кои интеграции (Stripe, push, cron) са настроени.
