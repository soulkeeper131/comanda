## 1. Какво е Ко Манда

Платформа за управление на имоти: почистване, обходи, инспекции, ремонти.

**Три роли:**
- **Клиент** — собственик на имот. Плаща абонамент, вижда какво е свършено, решава по оферти.
- **Инспектор** — работи на терен. Изпълнява обходи, качва снимки, отбелязва проблеми.
- **Админ** — управлява всичко: шаблони, възлагане, оферти, цени.

**Обещанието към клиента:** „виждате доказателство какво е свършено."

**Стек:** Next.js 14, TypeScript, Drizzle + SQLite, Tailwind. Деплой на Coolify,
домейн `comanda.blv.bg`.

## 2. Какво работи днес

### Сигурност — завършена

| Преди | Сега |
|---|---|
| 43 от 53 routes без никаква проверка | 0 непокрити |
| Сесия с 32-битов хеш, брутфорсваем за секунди | HMAC-SHA256 |
| `curl /api/properties` връщаше чужди адреси и GPS | 401 без сесия, филтрирано с нея |
| Всеки логнат можеше да си вдигне ролята до админ | Само админ пипа роли |
| `/api/reset-passwords` триеше базата анонимно | CLI скрипт с двойна защита |
| Паролите `admin1234` на публичната login страница | Премахнати |
| Снимките — публични по UUID | Зад проверка на собственост |
| `/api/email/send` — отворен мейл релей | Само админ |

### Процесна логика — завършена

- **Задължително доказателство.** Стъпка с `proof_type: "photo"` не се отмята без
  снимка. Втора бариера при завършване на обход.
- **Геофенсинг.** Check-in проверява разстоянието до имота.
- **Админски override.** Може да прескочи и двете проверки, но само с причина
  (мин. 5 знака), записана с автор и време. Прескачането се вижда в отчета.
- **Преходи на офертата.** `pending → accepted → paid → in_progress → done`.
  Клиент не може да сложи `paid`; админ не може да приеме от името на клиента.
- **Отказ на задача** със статус `cancelled` и причина.
- **Имейли до клиента** при нова оферта, завършен обход и отказ.

### Коректност

- TypeScript вече не е изключен на билда — криеше 16 грешки, сред тях счупени PDF отчети
- Една чиста Drizzle миграция вместо три разминаващи се източника
- Премахнати N+1 заявки (`/api/properties` правеше до 300 заявки при 100 имота)
- **142 теста**, 0 TS грешки, билдът минава

### Клиентски път — нов

Клиентът вече не вижда табове. Влиза и вижда имота си:
**Предстои** → **Последно свършено** (със снимките) → **Чака решение** (оферти).
Клиент без имоти вижда покана да добави, не празен екран.

## 3. Какво е счупено

Това не са UI проблеми. Липсват парчета от бизнес модела.

### 3.1 Абонаментът не произвежда работа — БЛОКЕР

`plans` има поле `per_month: 4`, но **никой не създава обходите**. Клиент плаща
абонамент, а админът въвежда всяка задача ръчно.

Оттам идва усещането, че „възлагането и задачите са объркващи" — няма процес,
има ръчно въвеждане.

### 3.2 Пакетите в интерфейса не съществуват в базата — БЛОКЕР

`PlanSelector` показва три зашити константи (`year`, `winter`, `summer`).
Схемата очаква `plans.template_id` → реален шаблон. Заявката няма къде да отиде.

### 3.3 Приетата оферта увисва

Потокът стига до `in_progress`, но не се създава задача за ремонта. Клиентът е
платил, а в системата не се случва нищо.

### 3.4 Инспекторът вижда 7 таба на телефон

Работи на терен, с ръкавици, на слънце. `dashboard/page.tsx` е 1730 реда и
обслужва трите роли едновременно.

### 3.5 Emoji вместо икони

Рендират се различно на всяко устройство.

### Четирите, които блокират работата

Без тези отговори не мога да напиша генератора на обходи:

| № | Въпрос | Защо блокира |
|---|---|---|
| **1** | Какво точно продавате като абонамент — X обхода от една услуга, или пакет от няколко? | Определя схемата на пакета |
| **3** | Какви честоти? Седмично / двуседмично / месечно, или конкретни дни? | Определя правилото за генериране |
| **7** | Кой избира деня и часа — клиентът при заявка, или админът? | Без правило генераторът насрочва произволно |
| **20** | Кой изпълнява приет ремонт — създава ли се задача? | Иначе платена оферта увисва |

**Останалите 26 имат разумни стойности по подразбиране** — ще ги предложа и
можеш само да потвърдиш.

## 5. План за изпълнение

Осем задачи. Колоната **Модел** казва кой субагент я поема — по-евтин за
механичната работа, по-силен за тази с преценка.

| # | Задача | Модел | Зависи от |
|---|---|---|---|
| M1 | Каталог на пакетите (backend) | haiku | въпроси 1–3 |
| M2 | Заявка за абонамент | sonnet | M1 |
| M3 | **Генератор на обходи** | sonnet | M2, въпроси 7–9 |
| M4 | Пакетите в UI = пакетите в базата | sonnet | M3 |
| M5 | Икони вместо emoji | haiku | — |
| M6 | Инспекторски път за телефон | sonnet | въпроси 13–16 |
| M7 | Разбиване на монолита | sonnet | M6 |
| M8 | Документ за дизайнера | haiku | всичко |

**Критичен път:** M1 → M2 → M3 → M4. След него клиентът заявява пакет и
системата работи сама. Това е MVP-то.

**Може паралелно:** M5 и M6 не зависят от абонамента.

Детайлите по всяка задача — файлове, правила, проверки — са в
[`plans/2026-08-16-mvp-plan.md`](superpowers/plans/2026-08-16-mvp-plan.md).

### Готово е, когато

- [ ] Клиент заявява абонамент от каталога и вижда потвърждение
- [ ] Обходите се появяват сами, без админска намеса
- [ ] Второ пускане на генератора не дублира задачи
- [ ] Приета оферта създава задача за ремонт
- [ ] Инспекторът минава чеклист на телефон без да рови
- [ ] Никакви emoji в интерфейса
- [ ] `dashboard/page.tsx` под 300 реда
- [ ] Тестовете, типовете и билдът минават
- [ ] Документът за дизайнера е готов

## 6. Как се пуска локално

### Първо: `SESSION_SECRET`

Приложението **отказва да стартира** без него — нарочно, за да не тръгне с
познат ключ. Добави в `.env`:

```bash
node -e "console.log('SESSION_SECRET=' + require('crypto').randomBytes(32).toString('hex'))"
```

Същото важи и за Coolify — без тази променлива деплоят спира.

### Команди

```bash
npm install
npm run db:reset -- --yes    # чисти базата (иска потвърждение)
npm run db:seed              # пълни с тестови данни, отпечатва паролите
npm run dev
```

### Проверки

```bash
npm test                     # 142 теста
npx tsc --noEmit             # 0 грешки
npm run build                # трябва да мине
```
